## Executive summary: what is in the data, and what students should find

records are generated by `src/log-generator/generate_corelight_logs.py --seed 1` on every student
repo build. Same seed, same story every time; only the clock moves. The scenario's events sit at
fixed UTC business hours on the day before the build, which is why the handout says **last 48
hours**. Everything is shaped to match the real Corelight schema (reference capture:
`datasets/corelight/real-sample-corelight-ai-events.json`).

## Before class: regenerate the data (do this the morning of)

The generator anchors a 24-hour window ending **now**, but the scenario's clock times are fixed
UTC business hours on the *first* calendar day of that window: the rogue burst is always
**11:07 UTC yesterday** (relative to generation). So "last 24 hours" is fragile: data generated at
02:30 UTC stops matching it at 11:07 UTC the same day, mid-Lab 03. The handouts therefore say
**last 48 hours**. Regenerate on the day anyway, or the data falls outside even that.

```bash
cd src/log-generator
python3 generate_corelight_logs.py --seed 1 \
    --outdir ../../datasets/corelight/generated \
    --answer-key ../../datasets/corelight/generated/answer-key.json \
    --sysmon-in  ../../datasets/sysmon/sysmon-events-jan21-clean.xml \
    --sysmon-out ../../datasets/sysmon/generated/sysmon-retimed.xml
```

`--seed 1` keeps it deterministic, so the answer key below holds. `--anchor <YYYY-MM-DD>T17:00:00Z`
pins the window end if you'd rather generate the night before.

The `--sysmon-*` pair is **not optional** if you intend to run task 8 and the Lab 03 cross-source
pivot: it re-times the real Sysmon XML so PID 3565's process burst lands on the same host and
window as the network burst.

**Prints on success:** per-tag record counts and the window start → end. Sanity-check that the end
is roughly now.

`datasets/**/generated/` is git-ignored on purpose. Regenerate; don't commit.

## The four methods: what each one gets wrong

Run these on the projector *before* turning students loose, so they see the shape of the answers.

### Method 1: DNS to known AI domains

```
tag=corelight_dns json "id.orig_h" as src_ip query
| lookup -s -r AI_DOMAINS query Domain
| count by src_ip query | table src_ip query count
```

**Wrong because:** resolving is not using. The top hit is a machine that used nothing.

### Method 2: SSL SNI

```
tag=corelight_ssl json "id.orig_h" as src_ip "id.resp_h" as dst_ip server_name
| lookup -s -r AI_DOMAINS_PLUS_API server_name Domain
| count by src_ip server_name | table src_ip server_name count
```

**Wrong because:** QUIC/HTTP-3 produces no TLS record Zeek can parse. Method 2 is blind to it.

### Method 3: plaintext HTTP host/uri

```
tag=corelight_http json "id.orig_h" as src_ip host uri method
| count by src_ip host uri | table src_ip host uri count
```

**Wrong because:** nothing, but it only sees plaintext. It is also the **only** method that finds
self-hosted models, because no domain list will ever contain `ollama.dev.acme.corp`.

### Method 4: SSO logins (ties a host to a *person*)

```
tag=okta json application_hostname client_ip actor.alternateId as user
| lookup -s -r AI_DOMAINS_PLUS_API application_hostname Domain
| table user client_ip application_hostname
```

**Wrong because:** only covers apps behind your IdP. Shadow AI is definitionally the stuff that
isn't. Droppable for time.

## The correlation query: the point of the module

**Naming.** The handout calls this **the correlation query**, and each task says which search to
start from and what to change. A "Before the tasks" paragraph lists the four searches a student
should have working before task 1: the DNS query, the SNI query, their own HTTP query, and the
correlation query. Use the same words at the front of the room; "two-step" and "Method 3" are ambiguous as
instructions.

**One compound query.** The inner query builds a temporary table of *(host, resolved AI IP,
domain)*; the main query joins connections to it on **both** columns with a vectored `lookup`. No
saved resource, no waiting for search A, no key building. The older two-search form (`table -save`
in one search, `lookup -r` in the next) returns identical rows and is mentioned in the handout as
what the saved-resource menu does.

```
@ai_resolved {
  tag=corelight_dns json "id.orig_h" as src_ip query answers
  | lookup -s -r AI_DOMAINS_PLUS_API query Domain
  | regex -e answers "(?P<ip>\d+\.\d+\.\d+\.\d+)"
  | table src_ip ip query
};
tag=corelight_conn json "id.orig_h" as src_ip "id.resp_h" as dst_ip orig_bytes resp_bytes service
| lookup -s -r @ai_resolved [src_ip dst_ip] [src_ip ip] (query)
| stats count sum(orig_bytes) as up sum(resp_bytes) as down by src_ip query service
| table src_ip query service count up down
```

**Expected (measured):** exactly five rows: `10.13.20.112` copilot 35 · `10.13.20.221`
chatgpt 29 · `10.13.20.203` chatgpt **quic** 12 · `10.13.42.42` api.anthropic.com 79 (17.2 MB up) ·
`10.13.42.60` api.openai.com 7 (48 MB up).

**Why match on `[src_ip dst_ip]` and not the IP alone:** `legal-lt-77` connects to the same
Cloudflare address `chatgpt.com` resolves to. Matching on the IP alone marks an innocent host as an
AI user. Requiring that **this** host did **this** resolution is the module's thesis: draw it on
the whiteboard. The vectored lookup *is* that requirement, written down.

**Teaching the syntax** (three things students have not seen):
- `@name { … };` is an inner query; its `table` is a resource that exists only for this query.
- `lookup -r @name [a b] [colA colB] (extract)` matches two fields against two columns at once.
- `-s` drops non-matches. `-s -v` together keeps *only* non-matches, which gives you the advanced
  example below.

**Advanced example, for the room that gets it fast** (also the fastest route to task 4): everything
Method 2 sees that the correlation query does *not*, i.e. AI connections with **no matching DNS resolution
by that host**. One row comes back, and it is the DoH host:

```
@ai_resolved {
  tag=corelight_dns json "id.orig_h" as src_ip query answers
  | lookup -s -r AI_DOMAINS_PLUS_API query Domain
  | regex -e answers "(?P<ip>\d+\.\d+\.\d+\.\d+)"
  | table src_ip ip
};
tag=corelight_ssl json "id.orig_h" as src_ip "id.resp_h" as dst_ip server_name
| lookup -s -r AI_DOMAINS_PLUS_API server_name Domain
| lookup -s -v -r @ai_resolved [src_ip dst_ip] [src_ip ip] ()
| count by src_ip server_name | table src_ip server_name count
```
→ `10.13.20.190  api.anthropic.com  43` (eng-lt-190, DNS-over-HTTPS). Measured.

**If someone reaches for the two-search form** (`table -save AI_RESOLVED` then `lookup -r
AI_RESOLVED`): it still works, the cheatsheet has it, and its one gotcha is that A must finish and
register the resource before B runs (~15 s). The compound form has no such gap, which is the reason
to teach it.

## Every query in this lab, task by task

The handout gives students Methods 1 and 2 and the correlation query; everything else they build by
iterating. This is the complete set, one or more queries per task, each **run on the host
as a seat** with the output that came back. Filters use the `eval field == "value"` form; `grep -e
field value` does the same thing for exact text. The walkthroughs are never released to students,
so this section can be as explicit as it likes.

**Task 1: which host resolved the most different AI domains, and is it in Method 2?**
```
tag=corelight_dns json "id.orig_h" as src_ip query
| lookup -s -r AI_DOMAINS query Domain
| stats unique_count(query) as domains count by src_ip
| sort by domains desc | table src_ip domains count
```
```
src_ip        domains  count
10.13.20.155  6        12      <- the scanner
10.13.20.140  3        6       <- link previews
10.13.20.112  1        20
10.13.20.221  1        10
10.13.20.203  1        4
```
When did it happen, and does the host appear in the SSL log at all?
```
tag=corelight_dns json "id.orig_h" as src_ip query | eval src_ip == "10.13.20.155"
| lookup -s -r AI_DOMAINS query Domain
| stats min(TIMESTAMP) as first max(TIMESTAMP) as last count by src_ip
| table src_ip first last count
```
→ 12 queries between **02:00:44 and 02:01:02 UTC**: eighteen seconds, in the middle of the night.
```
tag=corelight_ssl json "id.orig_h" as src_ip server_name | eval src_ip == "10.13.20.155"
| count by server_name | table server_name count
```
→ `outlook.office365.com 5` and nothing else. It never connected to an AI host.

**Task 2:** the compound correlation query above. Five rows.

**Task 3: the QUIC host.** What services does `10.13.20.203` actually use, and what does the SSL log
hold for it?
```
tag=corelight_conn json "id.orig_h" as src_ip "id.resp_h" as dst_ip service
| eval src_ip == "10.13.20.203" | count by dst_ip service | sort by count desc
| table dst_ip service count
```
→ `172.64.155.209 quic 8`, `104.18.32.47 quic 4`, `52.96.165.2 ssl 4` (that last one is Outlook).
```
tag=corelight_ssl json "id.orig_h" as src_ip server_name | eval src_ip == "10.13.20.203"
| count by server_name | table server_name count
```
→ only `outlook.office365.com 4`. Twelve QUIC connections to ChatGPT, zero SSL records: no
handshake for Zeek to write a `server_name` into.

**Task 4: the DoH host.** Every DNS query `10.13.20.190` made, and what its SNI says it did:
```
tag=corelight_dns json "id.orig_h" as src_ip query | eval src_ip == "10.13.20.190"
| count by query | table query count
```
→ `outlook.office365.com 10`, **`cloudflare-dns.com 2`**. That is the whole DNS story for this host.
```
tag=corelight_ssl json "id.orig_h" as src_ip server_name | eval src_ip == "10.13.20.190"
| count by server_name | table server_name count
```
→ `api.anthropic.com 43`, `cloudflare-dns.com 6`, `outlook.office365.com 5`. Forty-three TLS
sessions to Anthropic with no DNS record for it: the resolution went inside the DoH channel.

**Task 5: the decoy.** Who talks to `104.18.32.47`, with which SNI, and who resolved `chatgpt.com`
to it?
```
tag=corelight_ssl json "id.orig_h" as src_ip "id.resp_h" as dst_ip server_name
| eval dst_ip == "104.18.32.47" | count by src_ip server_name | table src_ip server_name count
```
→ `10.13.20.221 chatgpt.com 29` and `10.13.20.77 www.cloudflare-fronted-recipes.example 3`. Same
IP, two different sites.
```
tag=corelight_dns json "id.orig_h" as src_ip query | eval query == "chatgpt.com"
| count by src_ip | table src_ip count
```
→ 221, 203, 155. **Not 77.**
```
tag=corelight_dns json "id.orig_h" as src_ip query | eval src_ip == "10.13.20.77"
| count by query | table query count
```
→ `outlook.office365.com 16`, `www.cloudflare-fronted-recipes.example 6`. legal-lt-77 never asked
about ChatGPT. Not AI usage.

**Task 6: the self-hosted model.**
```
tag=corelight_http json "id.orig_h" as src_ip "id.resp_p" as port host uri method
| eval src_ip == "10.13.42.51" | count by host port uri | sort by count desc
| table host port uri count
```
→ `mcp-gateway.acme.corp :8080 /mcp 20`; `ollama.dev.acme.corp :11434 /v1/chat/completions 6`,
`/api/generate 5`, `/api/tags 4`, `/api/chat 3`. Internal names, plaintext, ports 8080 and 11434.
No list contains them; only Method 3 sees them.

**Task 7:** the biggest-upload query in the answer key below (`10.13.42.60`, 48,000,000 bytes).

**Task 8: find the incident without being told the host.** Two ways in, then the window.
Failed connections:
```
tag=corelight_conn json "id.orig_h" as src_ip "id.resp_h" as dst_ip conn_state
| eval conn_state != "SF" | count by src_ip dst_ip conn_state | sort by count desc
| table src_ip dst_ip conn_state count
```
→ every failed connection in the dataset belongs to **`10.13.42.42`**: `185.220.101.47` S0 ×3 and
REJ ×1, `169.254.169.254` S0 ×2.
Upload-heavy pairs (more than five times as many bytes out as in):
```
tag=corelight_conn json "id.orig_h" as src_ip "id.resp_h" as dst_ip orig_bytes resp_bytes
| stats count sum(orig_bytes) as up sum(resp_bytes) as down by src_ip dst_ip
| eval up > down * 5 | sort by up desc | table src_ip dst_ip count up down
```
→ `10.13.42.60 → 162.159.140.245` (7 conns, 48 MB, the CI runner) and `10.13.42.42 →
160.79.104.10` (79 conns, 17.2 MB up / 1.3 MB down). Two hosts, two different stories.
The window:
```
tag=corelight_conn json "id.orig_h" as src_ip "id.resp_h" as dst_ip
    orig_bytes resp_bytes conn_state
| eval src_ip == "10.13.42.42"
| stats count sum(orig_bytes) as up sum(resp_bytes) as down
    min(TIMESTAMP) as first max(TIMESTAMP) as last by dst_ip conn_state
| table dst_ip conn_state count up down first last
```
→ `160.79.104.10` (api.anthropic.com) SF ×79 from **11:07:56 to 11:15:48**; metadata probes at
11:11; the `185.220.101.47:4444` attempts 11:13 to 11:15. Eight minutes, ~10 connections a minute.
For the projector: `… | eval src_ip == "10.13.42.42" | count by dst_ip | chart count by dst_ip`
shows the burst as a spike. **Write down 11:07 to 11:15**; Lab 03's PID 3565 runs 11:07:53 to
11:14:55.

## Gravwell syntax gotchas

Have these ready; students will hit all of them.

- **Quoting in `json` is not cosmetic.** Quote a field name only when the key literally contains
  a dot: Zeek/Corelight does (`json "id.orig_h" as src_ip`). Okta *nests*
  (`{"actor":{"alternateId":…}}`), so the path must be **unquoted**: `json actor.alternateId as
  user`. Quoting a nested path returns an **empty column with no error**, which is the worst kind of
  failure.
- **Vectored `lookup`** (`[src_ip dst_ip] [src_ip ip]`) matches two fields at once, so nothing needs
  to build a glued key (the earlier `eval setEnum` / `concat` forms are gone).
  For a calculated field, `eval x = a / b` works; `eval setEnum(...)` is the
  legacy spelling and is gone from the course.
- **`lookup -s -r RESOURCE <field> <column>`**: `-s` for strict, `-r` names the resource.
- **`regex -e <field> "(?P<name>...)"`** pulls a capture out of a field into a new one, that's how
  the answer IP comes out of the DNS `answers` array.
- **`grep -e <field> "pattern"`** filters on an enumerated value; bare `grep "pattern"` searches
  raw text.
- **`stats` aggregates:** `count sum total mean stddev variance min max unique_count`. There is no
  `values()` and no `count(predicate)`: set membership is the `table -save` → `lookup -r`
  pair, or a compound query.
- **`table` needs `Format: csv`** if you're driving `/api/search/direct` from the CLI, and that
  endpoint wants RFC3339 timestamps.
